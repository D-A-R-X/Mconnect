JOINT CP - WEB VISIBILITY API / BACKEND HANDOFF
Date: 2026-09-01

ISSUE
Completed Joint CP visits created from Android exist and are visible on mobile,
but the second Joint CP participant (or a web staff filter for that participant)
cannot see the visit in the web CP list.

CONFIRMED MOBILE CREATE CONTRACT (ALREADY WORKING)
POST /api/marketing/clientPlaceVisits/create
Authorization: Bearer <session_token>
Content-Type: application/json

Joint CP request fields:

  "clientName": "Vinoth",

Expected success:
HTTP 200
{
  "success": true,
  "visitId": "<clientPlaceVisits_id>"
}

The server must validate exactly two different active staff, choose the senior
staff as the parent visit's assignedStaffId, and create one row for each staff
in clientPlaceVisitParticipants. Android already sends the required fields and
the current create route already forwards them.

ROOT CAUSE FOUND IN WEB/BACKEND QUERY
The parent clientPlaceVisits row contains only the primary/senior staff in
assignedStaffId. The second staff exists in clientPlaceVisitParticipants.

The mobile compact query already calls jointVisitIdsForStaff(...) and merges
the parent visit IDs found through the participant table. The web queries do
not consistently do this:

1. api.marketing.clientPlaceVisits.listPaginated (web table)
2. api.marketing.clientPlaceVisits.list (web calendar)
3. api.marketing.clientPlaceVisits.stats
4. CP visit export query/action

Their current staff-scope check only considers parent assignedStaffId,
telecallerStaffId, and proposedSiteVisit.avpStaffId. It does not consider rows
in clientPlaceVisitParticipants. Therefore the second Joint CP staff is removed
by scope filtering, and filtering by that staff also misses the Joint CP.

REQUIRED BACKEND FIX
Update every web CP read path above to treat a staff member as involved when
either condition is true:

A. parent.assignedStaffId == staffId
B. clientPlaceVisitParticipants contains
   visitId == parent._id AND staffId == staffId

Use the existing indexed participant lookup:

clientPlaceVisitParticipants.by_staffId_and_scheduledDate
  (staffId, scheduledDate)

Recommended implementation for list/listPaginated:

1. Resolve requester scope exactly as today.
2. Build jointLookupStaffIds from:
   - explicit assignedStaffId filter, otherwise
   - scoped viewer staff IDs.
3. Call jointVisitIdsForStaff(ctx, jointLookupStaffIds, rangeStart, rangeEnd).
4. Fetch and merge missing parent clientPlaceVisits rows before pagination.
5. De-duplicate by parent visit ID.
6. Apply staff filtering as:
   parent.assignedStaffId matches OR mergedJointVisitIds contains parent._id.
7. Apply status, outcome, search, and activity-date filters after merging.
8. Sort once, then paginate, so a Joint CP does not disappear between pages.

Important: bypass the current direct indexed fast path when an explicit staff
filter must include Joint CP companions. That fast path only indexes the parent
assignedStaffId and will always miss the second participant.

ERROR CONTRACT
- 400 INVALID_JOINT_CP: missing category, same staff twice, or not exactly two.
- 401 UNAUTHORIZED: missing/expired session.
- 403 FORBIDDEN: requester cannot view/create CP visits.
- 404 STAFF_NOT_FOUND or VISIT_NOT_FOUND.
- 409 JOINT_PARTICIPANTS_INCOMPLETE: parent exists but participant legs are
  missing/corrupt; return visitId and current participant count for diagnosis.
- 500 only for unexpected failures. Do not return partial create records.

3. Admin filter by A returns it; filter by B also returns it.

CONCLUSION
No new Android endpoint is required for this issue. Fix the existing web CP
read queries so they merge participant-table matches exactly as the mobile
compact query already does, then repair only any historical visits whose two
participant rows are missing.
